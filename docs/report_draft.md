# Scheduler Automation 工程实践报告 / 使用报告

## 一、项目概述

### 1.1 项目名称

Scheduler Automation：面向本地研发场景的任务调度与自动实施原型系统。

### 1.2 项目目标

本项目旨在构建一个可落地的研发调度原型，将“需求收敛、方案生成、代码实施、测试评审、问题修复、发布门禁”串联为一条可执行工作流。系统不是传统意义上的项目管理平台，而是一个围绕实际代码目录运行的工程执行控制台，强调任务和本地项目之间的强绑定关系，强调需求确认后的自动推进能力，以及阶段状态、产物、日志的持续留痕。

### 1.3 项目定位

系统当前定位为“工程自动化调度器初版”，主要服务于如下场景：

- 本地单项目或小团队协作研发场景；
- 需要围绕真实代码目录开展需求、开发、测试闭环的场景；
- 希望将 AI 辅助能力嵌入软件实施流程，而不是仅用于文档问答的场景；
- 需要保留阶段文档、执行日志、测试评审和发布门禁信息的场景。

## 二、问题定义与背景

### 2.1 要解决的核心问题

在常见的软件研发过程中，需求确认、开发实施、测试验证往往分散在多个工具中进行：

- 需求记录在聊天工具、文档平台或工单系统中；
- 开发在 IDE 与代码仓库中执行；
- 测试依赖手工验证或零散脚本；
- 过程状态和中间结论缺乏统一留痕；
- 任务从“可讨论”走向“可交付”的过程中，容易出现信息断层。

传统任务管理工具虽然可以记录阶段，但通常无法直接与本地代码目录、文件修改、测试命令形成闭环。另一方面，通用 AI 工具虽然可以生成需求文档或代码建议，但多数停留在单轮问答，不具备完整的流程推进、状态管控和发布门禁能力。

因此，本项目定义的问题是：

**如何围绕本地真实项目目录，构建一套从需求确认到自动实施再到测试评审和发布判定的最小闭环工作流。**

### 2.2 背景与动机

项目设计的直接动机来自以下实际痛点：

1. 需求经常在没有收敛前就进入开发，导致返工；
2. 开发与测试不共享统一上下文，问题回流成本高；
3. AI 虽然能写方案，但不能真正推进代码落地时，使用价值有限；
4. 项目目录、任务状态、文档产物、日志记录分散，难以复盘；
5. 用户无法判断自动流程当前运行到哪里、是否卡住、下一步该做什么。

基于上述问题，本系统希望提供一个更工程化的路径：先绑定项目目录，再绑定任务，再进入可追踪的自动流程，而不是把 AI 仅仅当作文档生成器使用。

### 2.3 应用场景与业务价值

本系统适合以下应用场景：

- 本地单仓库研发辅助；
- 中小团队内部工具开发；
- 原型系统快速验证；
- 需求驱动的自动代码生成与测试验证；
- 演示“AI + 工程流程”能力的教学与汇报场景。

业务价值主要体现在：

1. **缩短从需求到实现的链路**  
   需求确认后可以直接进入自动化实施与测试流程。

2. **提升过程可追溯性**  
   每个任务都有独立的工作区、阶段文档、日志和状态文件。

3. **降低多工具切换成本**  
   将项目选择、任务管理、工作区浏览、代码提案、测试执行整合到统一界面。

4. **提升 AI 使用的工程有效性**  
   不只生成说明文档，而是将 AI 输出纳入“可执行、可验证、可回流”的流程中。

## 三、技术方案架构设计 / 业务方案设计

### 3.1 整体架构设计

系统采用前后端分离架构：

- 前端：React + TypeScript + Ant Design
- 后端：FastAPI
- 状态与任务持久化：本地文件系统
- 模型访问：OpenAI 兼容接口
- 部署方式：Docker 部署 / 本机开发部署两种模式

整体流程如下：

1. 用户打开系统；
2. 从本地磁盘目录中选择项目目录；
3. 系统创建或打开项目，并建立 `root_path` 绑定；
4. 在项目内创建任务；
5. 用户与产品经理阶段进行需求收敛；
6. 需求确认后，系统在后台启动自动流程；
7. 自动流程依次执行产品规划、实施方案、代码修改、测试评审；
8. 若测试失败，则进入修复回路或方案回流；
9. 若满足发布门禁，则进入发布阶段；
10. 所有阶段文档、日志与状态被持续写回任务目录。

### 3.2 核心业务流程

当前版本的业务流程可概括为：

`打开项目 -> 创建任务 -> 收敛需求 -> 确认需求 -> 后台自动流程 -> 生成 spec -> 生成 implementation -> 写代码 -> 跑测试 -> tester 评审 -> 修复/回流 -> 发布判定`

其中关键控制点包括：

- `root_path` 必须绑定到具体项目目录；
- 未确认需求前不能进入实施；
- 自动流程在后台执行，不阻塞前端请求；
- `workflow_state.json` 用于持久化记录当前轮次、当前阶段、当前步骤、错误、门禁结果；
- `release gate` 用于决定是否真正允许进入发布阶段。

### 3.3 核心模块划分

#### 3.3.1 项目管理模块

负责项目创建、目录绑定、项目列表查询、已有项目打开、目录根浏览。

关键能力：

- 记录项目基础信息；
- 保存 `root_path`；
- 支持项目与任务关联；
- 支持 Docker 下的目录映射浏览；
- 支持通过 `open-roots` 从挂载磁盘根开始选择目录。

#### 3.3.2 任务工作流模块

负责任务的生命周期管理，是系统的中枢模块。

关键能力：

- 创建任务；
- 推进任务阶段；
- 管理 `requirements.json`；
- 管理 `workflow_state.json`；
- 管理 `request.md`、`spec.md`、`implementation.md`、`review.md`、`fixes.md`、`release.md`、`journal.md` 等任务产物。

#### 3.3.3 需求收敛模块

负责在正式实施前收敛需求，避免未经确认的任务直接进入开发。

关键能力：

- 记录用户补充的需求消息；
- 根据当前会话自动收敛需求；
- 输出建议摘要；
- 支持“确认需求并启动流程”的一体化入口。

#### 3.3.4 自动编排模块

负责串行执行产品、开发、测试三类阶段动作。

关键能力：

- 后台启动工作流；
- 阶段进度更新；
- 文件产物生成；
- 测试失败后的修复回路；
- 方案层问题的回流；
- 发布门禁判断。

#### 3.3.5 项目工作区模块

负责围绕项目目录进行文件浏览、代码修改提案与测试执行。

关键能力：

- 浏览绑定目录的文件树；
- 读取具体文件内容；
- 生成修改提案；
- 应用文件变更；
- 在项目目录下执行测试命令。

#### 3.3.6 模型接入模块

负责连接外部大模型能力。

关键能力：

- 支持 OpenAI 兼容接口；
- 配置 API Key、Base URL、Model；
- 为产品经理、开发代理、测试代理提供不同角色提示词；
- 在超时时返回明确失败信息。

## 四、核心功能实现说明

### 4.1 项目目录绑定机制

本系统区别于普通任务管理工具的第一点，在于任务并不是孤立存在，而是必须依附于项目目录。

项目创建后会保存 `root_path`，后续工作区浏览、代码修改、测试执行都通过 `project_id -> root_path -> Workspace` 的链路定位具体目录。这样可以确保：

- 当前任务针对的是哪一个本地项目目录是明确的；
- 文件浏览和测试执行都发生在正确的代码上下文中；
- 同一系统可以管理多个项目，而不是只能面向单一固定目录。

### 4.2 需求确认与需求收敛

系统在任务详细页提供需求收敛能力。用户可以持续补充需求、边界条件和验收标准，系统会根据当前会话判断下一步是“继续补充”还是“可以确认摘要”。

一旦需求摘要被确认：

- 任务的 `requirement_status` 变为 `confirmed`；
- `requirements.json` 中的 `summary` 被锁定；
- 未确认前禁止进入 `implement` 阶段的限制被解除；
- 后续的自动编排流程可以启动。

该设计的核心价值在于防止“边开发边猜需求”，将需求确认作为真正的流程闸门。

### 4.3 后台自动流程

为避免前端长时间等待导致“按钮一直转圈”的问题，系统已将自动流程改为后台任务：

1. 前端点击“确认需求并启动流程”；
2. 接口立即返回；
3. 后台创建自动流程任务；
4. 前端轮询 `workflow_state`；
5. 页面持续展示当前状态、当前步骤和说明。

这样做的好处是：

- 用户不再被一个长请求阻塞；
- LLM 调用、文件生成、测试执行的耗时被转移到后台；
- 即使流程失败，也会通过状态和日志显式反馈，而不是静默卡住。

### 4.4 阶段文档先行机制

系统不是直接“盲目改代码”，而是先生成阶段文档：

- `spec.md`：产品规划；
- `implementation.md`：实施方案；
- `review.md`：测试评审；

阶段文档会作为流程产物与可视化依据，保证自动实施具备一定的可解释性。用户不仅能看到最终结果，也能看到各阶段的中间产出和判断依据。

### 4.5 自动修复与方案回流

如果测试代理认为当前问题属于实现层缺陷，则系统进入 `fix` 回路：

- 记录失败输出；
- 生成修复指令；
- 重新执行开发与测试流程。

如果测试代理认为问题属于需求或方案边界不清，则系统进入 `spec` 回流：

- 在 `spec.md` 中写入反馈；
- 重新生成产品规划；
- 再重新生成实施方案与代码修改。

这使得系统不只是一次性执行器，而具备初步的闭环修正能力。

### 4.6 发布门禁

当前系统的发布判定不是简单看“测试是否执行完”，而是综合以下条件：

- 测试退出码必须为 0；
- tester 不能给出阻塞结论；
- tester 的建议动作必须为 `release`；
- 不存在 `blocking` 问题；
- 不存在 `high` 严重级别问题。

只有这些条件满足时，系统才会认定任务达到发布条件，并写入 `release.md`。

## 六、创新说明

### 6.1 相比主流项目管理工具的差异化

主流任务管理工具通常关注任务记录、协作看板和状态流转，但不直接触达本地真实代码目录。本系统的创新点在于：

1. **项目目录绑定**
   - 任务不是抽象存在，而是绑定到真实本地项目目录；
   - 工作区、代码提案、测试命令都直接基于该目录执行。

2. **需求确认是工程闸门**
   - 系统将需求确认从“形式化记录”提升为“流程前置条件”；
   - 未确认需求不能直接进入实施阶段。

3. **自动流程具备阶段留痕**
   - 自动流程不是一个黑箱命令，而是持续更新状态、日志和阶段文档；
   - 用户能够追踪当前运行到哪一步。

4. **引入测试代理与发布门禁**
   - 不是只做代码生成，还引入了测试评审与发布判定；
   - 从“会生成”提升到“能判断是否可发”。

5. **具备修复回路与方案回流**
   - 当前版本已支持有限次数的自动修复；
   - 支持根据 tester 判断回到方案阶段，而不是只会无脑重试。

### 6.2 与通用 AI 编程工具的差异

通用 AI 编程工具大多提供代码补全、对话式问答或单次修改建议，而本系统更强调：

- 任务级上下文；
- 阶段化推进；
- 文档先行；
- 测试回流；
- 发布门禁；
- 本地代码目录绑定。

因此本系统更像“AI 驱动的工程工作流壳层”，而不仅仅是“对话式编码助手”。

## 七、落地部署方案

### 7.1 Docker 部署方式

这是当前最适合交付和复现的方式。

部署准备：

```powershell
$env:PROJECT_ROOT="D:\Work\Scheduler"
$env:HOST_C_PATH="C:\"
$env:HOST_D_PATH="D:\"
docker compose up -d --build
```

说明：

- `PROJECT_ROOT`：调度器仓库自身路径；
- `HOST_C_PATH`：宿主机 C 盘挂载到容器；
- `HOST_D_PATH`：宿主机 D 盘挂载到容器。

系统访问方式：

- Web / API：`http://localhost`
- 健康检查：`http://localhost/healthz`

运维注意事项：

1. Docker 只能访问已挂载进容器的主机路径；
2. 如果“打开文件夹”看不到目录，优先检查磁盘挂载是否生效；
3. 修改代码后需要 `docker compose up -d --build` 重建；
4. 如需排查问题，可通过 `docker compose logs -f` 查看日志。

### 7.2 本机开发模式

适合研发调试，尤其适合排查目录权限与文件路径问题。

后端启动：

```powershell
$env:PYTHONPATH="src"
.venv\Scripts\python.exe -m uvicorn scheduler_automation.api.app:app --host 0.0.0.0 --port 8000
```

前端启动：

```powershell
cd src/web
npm install
npm run dev
```

访问地址：

- `http://localhost:5173`

本机模式优势：

- 更适合调试 Windows 原始路径；
- 不受 Docker 文件挂载边界影响；
- 更适合联调前端和后端。

### 7.3 依赖环境说明

核心依赖包括：

- Python 3.13 运行时；
- FastAPI；
- Node.js / npm；
- React + TypeScript；
- Docker Desktop（Docker 模式时）；
- 可用的 OpenAI 兼容模型服务。

### 7.4 模型兼容性与使用建议

当前系统支持任何 OpenAI 兼容接口，只要能提供：

- API Key
- Base URL
- Model

兼容建议：

1. **开发与测试场景**
   - 优先选择具备较强代码生成能力和结构化输出稳定性的模型；
   - 模型必须能稳定输出 JSON，以支持 tester 结构化结论。

2. **成本敏感场景**
   - 需求收敛与产品规划阶段可以使用中等规模模型；
   - 实施方案与代码修改阶段建议使用更强的代码模型。

3. **本地部署场景**
   - 如果使用本地模型网关，需确保接口严格兼容 OpenAI Chat Completions；
   - 同时注意响应延迟，避免过长超时。

4. **实际使用建议**
   - 产品规划与测试评审对结构化输出要求较高；
   - 开发阶段对代码一致性和文件级修改能力要求较高；
   - 如果模型不稳定，优先从设置页测试连接与输出质量。

## 九、当前局限与后续优化方向

虽然系统已具备最小闭环，但当前仍属于初版，主要局限包括：

1. 前端仍采用轮询，而非 WebSocket / SSE 实时推送；
2. tester 结构化结论已具备，但问题分级体系仍可继续增强；
3. 自动修复与方案回流目前是有界循环，不是无限自收敛；
4. 不同模型对结构化输出稳定性存在差异；
5. Word 报告中的截图需要结合实际运行界面补充。

下一步优化建议：

1. 引入实时事件流，提高前台进度刷新体验；
2. 增加后台任务管理与任务取消能力；
3. 增加更细粒度的测试计划生成与用例分类；
4. 增加人工介入后的恢复动作；
5. 完善面向团队协作的权限与审计能力。

---

## 十、总结

Scheduler Automation 项目的核心意义不在于替代传统项目管理工具，而在于验证一种更贴近工程落地的自动化工作方式：让任务不再只是文档记录，而是能够绑定本地代码目录、形成需求闸门、触发后台自动实施、生成中间产物、执行测试并做发布判定。

从工程实践角度看，本项目已经完成了一个具备现实意义的初步闭环：

- 需求可收敛；
- 任务可绑定；
- 目录可打开；
- 代码可修改；
- 测试可执行；
- 问题可回流；
- 状态可追踪；
- 发布可判定。

这为后续继续扩展为更完整的 AI 工程调度器提供了坚实基础，也为“AI 从文档辅助走向工程执行”提供了一个具体、可演示、可部署的实现样本。
